# Agent stack

Claude Code, Codex, and pi share one instruction file and one set of skills.

- `AGENTS-global.md` is linked as `~/.claude/CLAUDE.md`, `~/.codex/AGENTS.md`, and `~/.pi/agent/AGENTS.md`. pi-only rules live in `pi/APPEND_SYSTEM.md`.
- `skills/shared/` goes to `~/.claude/skills` and `~/.agents/skills` (Codex and pi). `skills/claude/` is Claude-only. `skills/codex/` also goes to `~/.agents/skills`, so Codex and pi both get it.
- Subagents live in `claude/agents/`, `codex/agents/`, and `pi/agents/`, linked as `~/.claude/agents`, `~/.codex/agents`, and `~/.pi/agent/agents`. Each tool has `auditor` and `recall`. Claude and Codex also have `researcher`, and pi uses its built-in one. Codex agents cannot be made read-only, so read-only is only an instruction there.
- Guard hooks live in `hooks/`, linked as `~/.agents/hooks`. `hooks/guard.sh` execs `agent-guard`, a Go binary built from `guard/` by `modules/overlays/agent-guard.nix`, and exits 2 when it is not on PATH. `guard/checks.go` is the one ordered table of checks and the tools each runs on, with one file per check, and `guard/argspec.go` holds each program's options that take a value. It parses a shell command once, following each `cd`, `pushd`, subshell, and literal variable so every call knows its directory, the files it writes, and the scripts it runs, then runs each check and prints one decision. A change under `guard/` goes live with `just switch`. Claude (`claude/settings.json`), Codex (`codex/hooks.json`), and pi (`pi/extensions/guards.ts`) each call it once per event, naming the harness. Claude's PreToolUse entry sets `onFailure: block`, so a guard that hangs past its timeout or prints bad output blocks the call too. Codex also runs `tmux-bell.sh` and `tmux-agent-resume.sh` from `codex/hooks.json` (trust them once with `/hooks`, and again after an entry there changes).
- Commands only agents run live in `bin/`, linked whole as `~/.agents/bin`, so a change there is live at once. Callers name them by path with their `.sh`: `new-scratch.sh` makes a task's scratch folder for `AGENTS-global.md`'s scratch rule, and `agent-side.sh` opens the `/side` split for Claude's side skill and pi's `side-conversations.ts`.

## Guards

All of these run in Claude and pi. Codex runs the shell-command checks, but it has no "ask" decision and applies a rewrite only with an allow, so under Codex `agent-guard` turns every ask into a deny and drops the attribution rewrite. `codex/rules/default.rules` still forbids `git push` and `gh pr` writes, which holds even while the hook is untrusted.

Before a shell command:

- `git-add-before-nix`: no flake evaluation while new files are untracked
- `strip-claude-attribution`: removes Claude attribution from commit messages
- `block-global-search`: no `find`, `fd`, `rg`, `grep` (and `egrep`, `fgrep`, `ugrep`), `ag`, or `ack` rooted at `/`, `~`, `/nix`, or another filesystem-wide directory, including a relative search after a `cd` there, and no relative search after an unquoted `cd $var` / `cd $(...)` that could land in `$HOME`. A search of `.` with no `cd` stays allowed, so a session started in `~` can still search it
- `block-unresolved-write`: no write to a path the guard cannot place, either a relative write after a `cd` it cannot follow (`cd "$d"`) or a path built from a value it cannot know (`$(...)/f`), since it cannot tell which file that is. A write whose directory is a `$(new-scratch.sh ...)` folder, or resolves under a `.eric/scratch/` tree, is allowed even with a built-up file name, since that tree is untracked. A variable an `&&` branch set to a literal (such as `cd dir && v=x`) resolves for a redirect target, checked under both its literal and its empty value, so `echo y > "$v/f"` lands; elsewhere, including a copier's target, it stays unknown
- `block-symlink-clobber`: no mv, cp, ln, install, rsync, dd, tee, redirect, in-place sed/perl, or truncate onto any symlink, including a copy into a folder under the source's name
- `ask-dangerous-git`: asks before rebase, reset, clean, replace, a checkout of an existing path, `gh pr checkout --force`, and other history changes
- `ask-defaults-write`: asks before `defaults write`, `delete`, `import`, or `rename`, which change app or system settings. Reads run
- `block-agent-push`: agent pushes (`git push`, `send-pack`, `subtree push`, `lfs push`) follow `git config eric-agent.push` in every repo the command pushes from: unset or `off` (default) denies, `ask` (approve each; Codex denies it), or `on` (Codex still forbids `git push` in `codex/rules/default.rules`). A push of an `agent-test-` branch, named in a refspec or checked out, is always denied
- `block-gh-write`: agents use `gh` read-only: only the reads and local-only downloads and checkouts in `ghRead` (`guard/block_gh_write.go`), `--help`, `help`, `version`, and `gh api` GETs run (fields need an explicit `-X GET`, since gh otherwise sends them as a POST). A `gh api graphql` read runs when it passes one literal `-f query=...` with no mutation and no `$`. In Codex this hook is the allowlist, because a `forbidden` rule for `gh` would also block the reads
- `block-agent-commit`: agent commits, merges, reverts, cherry-picks, `git am`, `update-ref`, `subtree`, `fast-import`, a `branch -f`, `-M`, or `-C`, a fetch or pull refspec into a local branch, and any `pull` without `--ff-only` follow `git config eric-agent.commit` in every repo the command commits in: `off` (default), `ask` (approve each; Codex denies it), `branch` (never on `main` or `master`, and never a command that can move a branch other than the checked-out one), or `on`. `commit-tree` runs, since it only writes an object that another command must still move a branch onto. On an `agent-test-` branch, the agent's own, a command that moves only the checked-out branch needs no setting. `--abort`, `--quit`, and `commit --dry-run` always run, as does `push --dry-run` or `-n` in `block-agent-push`. Both gates deny `-c` or `--config-env` aliases and includes, `GIT_DIR`, `GIT_WORK_TREE`, `GIT_COMMON_DIR`, `GIT_INDEX_FILE`, and `GIT_CONFIG*` assignments anywhere in the command, and a gated command with `--git-dir`, `--work-tree`, `core.worktree`, `find -execdir`, or a repo the guard cannot resolve (a `cd` or `-C` through an unknown variable), since each can move git past the repo or config the gate reads. Each `cd`, `pushd`, `-C`, `env -C`, and `sudo -D` before the command is followed. Rebase stays with `ask-dangerous-git`
- `block-git-config-edit`: no redirect, tee, or other write onto a `.git` config file, `~/.gitconfig`, or `~/.config/git/config`, and no tool outside the `readers` list in `guard/block_git_config_edit.go` naming one, so config changes go through `git config`. Only the user sets `eric-agent`, `alias`, and `include` keys, so a `git config` that names one must be a read
- `block-hook-bypass`: no setting `core.hooksPath`, no write onto a file under `.git/hooks` or onto `.git/info/attributes`, and no `--no-verify` (or `commit -n`) on commit, merge, pull, or push, each of which repoints or skips the git hooks that enforce repo policy. `.git/info/attributes` holds the `agent-verbatim` and `agent-generated` opt-outs, which are read only from there, so a `.gitattributes` the agent writes sets no opt-out
- `block-eric-top`: no write into a file or folder directly under `~/.eric/` or a repo's `.eric/` other than the entries the global instructions name, or a `.eric/<entry>` the AGENTS.md beside it names
- `block-shell-edit`: no sed/perl in place, truncate, scripts that write, or redirects, cp, mv, ln, install, rsync, or dd onto git-tracked text files, including a copy into a folder under the source's name. Binary files, which the edit tool cannot change, are exempt
- `block-sudo-probe`: no `sudo -n` on macOS, where Touch ID approves a plain `sudo`
- `block-exec-flags`: no `fd -x`, `rg --pre` or `--hostname-bin`, `sort -o` or `--compress-program`, `tree -o`, `uniq` with an output file, or `git diff`/`log`/`show --output`, which would run or write through tools the agents approve as read-only
- `block-rm`: no `rm`, `unlink`, `find -delete`, or `rsync --delete` or `--remove-source-files`, since `trash` keeps a way back
- `block-mux-kill`: no kill of a session, window, pane, or server on the user's tmux or rex, through a subcommand, `rex api call`, `rex do` Lua, `respawn -k`, `scratch rm`, or `kill` of the pids `pgrep` finds. A private tmux `-L` server, or `-S` socket outside the user's `tmux-<uid>` folder, or a rex server on the agent's own socket, stays the agent's to kill, and so does a rex session, tab, or pane whose label starts with `agent-test-`
- `block-pipe-head-tail`: warns (does not block) when output is piped into `head` or `tail`, or fed to one through `<(...)`, `>(...)`, or a here-string of a substitution, unless a `tee` to a file in the same pipeline saves it. The call runs and an `additionalContext` note says the rest of the output was dropped and how to capture it, since cost is per-invocation and a static check cannot tell a cheap peek from a lost build log. A `tee` that saves the output, `tail -n +N`, and `head` or `tail` on a file warn about nothing

`agent-guard` denies a command its zsh parser (`mvdan.cc/sh`, the library behind shfmt) cannot parse, and anything that runs code no check can see: a shell that reads its script from a pipe or `/dev/stdin`, an interpreter with no program file or `-c`, a csh, tcsh, or fish script, `xargs` that builds a command from its input, `BASH_ENV`, `ZDOTDIR`, `core.hooksPath`, zsh's `(e)` flag and code-running glob qualifiers, and a program named by a variable or substitution. A here-string, heredoc, `eval`, `watch`, `script -c`, `trap`, a tmux command string, `git submodule foreach`, `git bisect run`, a git `-c` setting that names a command, and a variable such as `GIT_PAGER` are checked like a `bash -c` script, at any depth. So is a git alias: a `!` alias is walked as its shell code from the repo's top level, and any other alias is expanded so every check reads the command it stands for. An alias the guard cannot read denies: one in a repo it cannot tell, one with more than one plain command as its text, or one at the end of a chain of more than five aliases. The command behind a wrapper or runner (`sudo`, `env`, `uv run`, `npx`, `nix run`, `direnv exec`, and the rest in `guard/parse.go`) is checked as a call of its own, and a wrapper option the guard does not know is read both ways, as a flag and as taking a value. `awk` or `sed` code that runs a command denies, and its writes count as writes. A walk past 10000 statements, as nested loops can reach, denies.

The guard reads shell, not other languages. Code an interpreter runs (`python -c`, a script file) is checked only by its write heuristics in `guard/call.go`. A shell, awk, or sed script file (`bash ./run.sh`, `awk -f prog`) is not read, and keys sent with `tmux send-keys` are not checked at all.

Before a file read or edit: `deny-symlink-path` (use the real path, not a managed symlink, and never write through a link that leads outside the nix-managed roots), `block-smart-punct` (smart punctuation in written content is normalized to ASCII under Claude, denied under codex/pi and in commit messages; the `agent-verbatim` opt-out lives in `.git/info/attributes`), `block-write-tracked` (no whole-file Write over a git-tracked file), `block-git-config-edit` (no Write or Edit of a `.git` config file), `block-eric-top` (no Write or Edit of a stray entry at the top of a `.eric/` folder).

After an edit: `treefmt-on-edit` (formats the file), `warn-comment-block` (flags comment blocks of four or more lines).

## pi

Extensions in `pi/extensions/` are linked per file into `~/.pi/agent/extensions` by `ai.nix`, so a new extension needs `just switch`. `guards.ts` runs no `Notification` or `SessionStart` hooks, so `tmux-agent-resume.ts` runs that hook itself. `pi/lib/` holds helpers for extensions, since pi loads every `.ts` in `extensions/` as an extension. `mcp.json` starts the `context7-mcp` and `cornell-confluence-mcp` wrappers from `ai.nix`, plus `railway mcp`.

## Tests

`go test ./...` in `guard/`, which the package build also runs, holds each check's cases in `guard/checks_test.go` and fails if a check in `guard/checks.go` has none. It also checks the table and that the walk reaches a call inside every shell construct. CI's `ai-agent-tests` job in `.github/workflows/check.yml` runs `hooks/test.sh` and the `pi/tests` suite. To run them locally, run that job's steps from the repo root, with `go` from the devShell. `test.sh` builds `agent-guard` from `guard/`, tests `guard.sh` and the other hook scripts, and fails if a script in `claude/settings.json` has no test, if the Claude matchers differ from `agent-guard tools pre` and `post`, or if this README does not name a check. So a new check is one function, one row in `checks.go`, an entry in `checks_test.go`, and a line here. The `pi/tests` suite runs the `agent-guard` on PATH, so locally it tests the installed binary until the next switch.
